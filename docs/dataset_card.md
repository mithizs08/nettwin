# Dataset card: NetTwin scenarios v1

Generated by `scripts/phase3_build_dataset.py`; every number below is copied from `results/phase3_dataset_summary.json`. All telemetry is synthetic. Topologies are public (Internet Topology Zoo, SNDlib) or generated. None of this is Telstra's network.

## What a scenario is

One simulated week (7 days, 5-minute steps, 2016 steps) on one topology: link utilisation, one-hop latency and discard counters per link; end-to-end latency and probe loss per synthetic service; observed events (lagged link status, PoP reachability, planned-maintenance log). Up to three faults per scenario after a one-day warmup, plus distractors (maintenance, telemetry gaps, probe gaps, event days, hot links). The simulator is described in `PLAN.md` section 4 and `src/nettwin/simulator.py`.

Simulator frozen at hash `dcdea81026a02ad6` (sha256 over `config.yaml`, `simulator.py`, `faults.py`, `synth.py`, `topology.py`, `kg.py`; full value in `results/simulator_freeze.json`).

## Variants

Every scenario is stored twice, from the same simulation run:
- `with_status`: status events and SNMP-style down links (util exactly 0, discards 0, one-hop latency missing). "util exactly 0 with latency missing" is a near-unique, realistic down-link signature (audit re-verify N2).
- `status_blind`: down links fully missing (like a telemetry gap) and no status or reachability events; the maintenance log stays. Observability flags are recomputed for this view.
Results for link_down and node_down must be reported on both variants.

## Layout and use

Root `data/datasets/v1` (gitignored; rebuild with the script):
- `observable/<split>/<variant>/<sid>/`: `links.parquet` (t, link, util, latency_ms, loss_pct), `services.parquet` (t, service, latency_ms, loss_pct), `observed_events.json`, `meta.json` (scenario id, topology, step count, step length, variant). This is the only tree detectors and the agent may read.
- `truth/<split>/<variant>/manifest.json`: per scenario the seed, faults with params, placement, impact, observability flags, maintenance, gaps and event days; `truth/<split>/<variant>/<sid>/labels.parquet`: per-link per-step labels (2 root, 1 symptomatic, 0 unaffected).
- Scenario ids are neutral (`tr`, `va`, `te`, `dv` plus a number). The observable tree holds no seed, since the seed plus the config would let anyone re-run the sampler and recover the faults.

## Known limitations (see `docs/decision_log.md`)

- Telemetry is synthetic; traffic follows a gravity model with a fixed daily shape. Services are synthetic (2 per PoP).
- Pre-registered difficulty target T2 was missed for routing_misconfig and link_flapping (too few subtle, too many obvious on validation), and T6 overlap with maintenance is above its 20% ceiling. Difficulty was not retuned to fix these.
- link_down, node_down and most flapping are easy in the with_status variant (status events and the down-link signature). Report them per type, never averaged with the hard types, and on both variants.
- Impact classes use relative latency thresholds tuned on validation; the mix differs by topology (see the per-topology breakdown in the summary JSON). Sparse, tree-like test networks (York, Peer1, Belnet2010) produce more unreachable services.
- AARNet (dev) was used to develop the simulator; its numbers are illustrative only.
